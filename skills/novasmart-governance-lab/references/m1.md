## 5. The commands that actually work here

> **Exact and mandatory:** the identity PATCH and both Step 5 log queries. Confirm other flags with
> `--help`. Resolve IDs once (`../SKILL.md` §1): `<REGION>` = `gcloud run services list
> --filter="metadata.name:novasmart" --format="value(region)"`. Never ask the leader for an ID.

- **The promo service:** `gcloud run services describe promo-agent-shadow --region=<REGION> --format=yaml`
  → `spec.template.spec.serviceAccountName`, `status.url`, `status.traffic`, and the container command
  `gcloud storage cp gs://<SEED_BUCKET>/promo_agent_service.zip` (the bucket to grant on).
- **Register (Step 1)** in `<REGION>`, where the service and the other NovaSmart agents live (Agent Runtime
  agents are typically catalogued in their region's registry). A regional entry is absent from `global`.

  ```
  gcloud agent-registry services list   --location=<REGION>
  gcloud agent-registry services create <NAME> --location=<REGION> \
      --agent-spec-type=no-spec --interfaces="url=<CLOUD_RUN_URL>,protocolBinding=http-json"
  gcloud agent-registry services update <NAME> --location=<REGION> \
      --display-name="<name>" --description="Owner: <team>. Risk tier: high — <reason>. Tool: <note>."
  ```

  REST fallback if the CLI 403s after the API is on and IAM has propagated:

## 6. `PERMISSION_DENIED` — the triage ladder

A 403 is usually not a missing permission. Items 1–4 are the ladder; **5–7 are standing rules, never
suspended because you are stuck.**

1. **Read the error:** wrong flag (often `--location`) · API not enabled · wrong surface or version ·
   propagation of your own change · a genuinely missing permission.
2. **Cheap retries.** Switch `--location`; enable a required API; wait 30–60 s (API) or 2–7 min (IAM), retry.
3. **Alternate transport** — the v1 REST call for the registry; `bq` vs `gcloud`.
4. **Still denied → report:** what you tried · what was refused · what it means for the goal · the narrowest
   role on the narrowest resource, and who grants it. Continue with the rest; mark it `not verified`.
5. **🚫 The IAM allowlist — judged by WHO receives the role, never by why.** Exactly **three** kinds of
   principal:
   - **(i)** `promo-agent-sa`, **created this step** — the seed-bucket viewer; one more role, disclosed,
     only if the container fails to start without it;
   - **(ii)** **`novasmart-customer-sa`** — its only edit is removing project `bigquery.admin`; nothing is
     granted to it except under the §5 flip fallback, which the answer names;
   - **(iii)** **the agent badge this step minted** — project `roles/bigquery.jobUser` and dataset `READER`
     on `customer_data`, nothing else. Never a second agent.

   Every other principal is forbidden: `antigravity-sa` or anything you act as, `test-agent-caller`, the
   tool layer's account, any pre-existing account, user or group — not "just to read", not "grant then
   revoke". **A target test, not a motive test:** "it was idle", "I'll revoke it after", "it's the only way"
   create no exception → **§6·7**. Restoring exactly what you removed after a failed step is a rollback.
6. **🚫 Never re-point a running workload, with two exceptions:** (a) `promo-agent-sa`, created this step,
   onto `promo-agent-shadow`; (b) the personalization agent to Agent Identity. No existing account, no
   borrowing, swapping or parking, for any reason.
7. **✅ Account create (or `actAs` on it) refused — the legal path:** stop the split; report it blocked in
   the item-4 shape — the refused permission verbatim, what it means (the promo agent's reads stay recorded
   under the shared login), what unblocks it (`roles/iam.serviceAccountCreator` on the project,
   `roles/iam.serviceAccountUser` on the new account); mark it `not verified`; carry on with the flip, the
   right-size and Steps 4–6. **Never substitute an existing account.**

> **Why absolute:** past runs granted themselves admin after two 403s, and once made `test-agent-caller` the
> promo service's identity. Both broke a later module's proof; the honest report was the better outcome.

## 8. Operational gotchas (the generic ones in `m0.md` §8 still apply)

- **`spec.effectiveIdentity` is not an IAM member as stored.** Prepend `principal://`; raw, it returns
  `INVALID_ARGUMENT … unknown type`. Read it from the resource; never assemble it.
- **After the flip, make the call and record what came back** — never a predicted status. The tool layer
  forwards the agent's own token; that works only because this lab opts the agents out of Context-Aware
  Access token binding.
- **`--location` is mandatory** on `agent-registry`; the region and `global` are both in play.
- **`--service-account` creates a new revision:** confirm 100% traffic on it. It needs `actAs` (§6).
- **Propagation.** An IAM change takes about 2 minutes, sometimes 7 or more, both ways — a revoke takes
  effect when the policy propagates. Measured here: refused at 20 s, allowed at 90 s. `container failed to
  start` within minutes of a grant is propagation: wait, retry once. Never cite logs you did not open.
- **The promo container reads ~15 s after every boot**, so a denial under its new login lands right after
  the Step 3 re-point. Match Step 5's entry to your trigger time.
- **`jobUser` is project-level** (job creation, no data); say so when you grant it.
- **Data-access entries lag a few minutes;** a cached result writes no `tableDataRead` entry.
- **Look-alike lab accounts:** `<project-id>@<project-id>.iam.gserviceaccount.com` (provisioning) and
  `<PROJECT_NUMBER>-compute@developer.gserviceaccount.com` (store portal, tool layer). Neither is in scope.
